# vulnetix Provider

Manage Vulnetix configuration as code. Every resource is one `vulnetix.com/v1` config document, generated from the kind schemas in [config-schemas](https://github.com/Vulnetix/config-schemas), and applied through the same server-side engine as `vulnetix config apply`.

Each resource is one config kind. Its arguments are the kind's `spec`, in snake case (`blockMalware` is `block_malware`), beside `name`, `labels` and `annotations` from its `metadata`. Every resource page shows a **Minimal** example (only the required arguments), an **Advanced** example (every argument) and how to import an existing object.

## Install

Terraform 1.11 or later, or OpenTofu 1.11 or later: the provider uses write-only arguments for secrets.

```terraform
terraform {
  required_providers {
    vulnetix = {
      source = "vulnetix/vulnetix"
    }
  }
}

# The token is read from VULNETIX_CONFIG_TOKEN when not set here. Keep it out
# of the configuration: pass it from your CI secret store.
provider "vulnetix" {
  # endpoint = "https://www.vulnetix.com/api/site/v1"
  # manager  = "terraform"
}
```

Run `terraform init` (or `tofu init`). OpenTofu reads the same `vulnetix/vulnetix` source from its own registry; nothing else changes.

## Authentication

The provider authenticates with a config management token (`vmt_...`), sent as `Authorization: Bearer`. A token acts as a service account of the tenant and carries a role and the kinds it may change:

- An owner or admin, signed in, issues one with `POST /v1/config/tokens` (`name`, `principalUuid` of a service account, `role`, `kinds`, `expiresInDays`). The token is in that answer only; rotate it with `POST /v1/config/tokens/{uuid}/rotate` and revoke it with `DELETE /v1/config/tokens/{uuid}`.
- Applying needs the `owner` or `admin` role and the kinds the configuration manages.
- Pass it as `VULNETIX_CONFIG_TOKEN`, from your CI secret store, rather than in the configuration.

`VULNETIX_ENDPOINT` points the provider at another API base URL, such as a staging tenant's.

## Ownership and drift

Every apply is recorded with the provider's `manager` (`terraform` by default). A GitOps `vulnetix config apply --prune` only deletes objects its own manager owns, so it leaves Terraform's alone, and Terraform cannot delete an object another manager owns.

Most kinds merge a document into the stored object, so a refresh only reads the arguments you set: the server's defaults never show as a diff. Import is the exception and reads every field.

## Secrets

A secret property is two arguments: `<name>_wo`, write-only, never in the plan or the state; and `<name>_wo_version`, a number to change when the secret should be sent again. Feed `<name>_wo` from an ephemeral variable or an ephemeral resource.

## Import

Import any object by its name (`metadata.name`); one-per-tenant kinds are named `default`:

```shell
terraform import vulnetix_quality_gate.default default
```

## Schema

### Optional

- `endpoint` (String) The Vulnetix API base URL. Defaults to `$VULNETIX_ENDPOINT`, then `https://www.vulnetix.com/api/site/v1`.
- `manager` (String) The manager recorded as the owner of every object this provider applies. A GitOps apply with `--prune` only deletes objects it manages itself. Defaults to `terraform`.
- `token` (String, Sensitive) A config management token (`vmt_...`). Defaults to `$VULNETIX_CONFIG_TOKEN`. Applying needs a token with the owner or admin role.
